Faculty Dashboard: Product and Architecture Documentation

Status: Draft v0.1. Scope: Department Coordinator, IET. Derived from the current React prototype (dc_dashboard.jsx) and the SOP tracker workbook (dc_sops_tracker.xlsx).

1. Product Requirements Document

1.1 Purpose

A single system where the Department Coordinator assigns work to faculty, sets deadlines, collects submissions, and sees who is on track, replacing the spreadsheet, email chasing and the Apps Script reminders currently used to run the department.

The problem today: submission status lives in email threads, teaching allocation lives in a sheet, and compliance (course files, evaluation, marks upload) is checked by hand each month. The coordinator finds out about problems late.

1.2 Roles

Role Who Access & Responsibilities
Coordinator (admin) Department Coordinator Full department administration: manage faculty directory, skills, courses, semester offerings, teaching allocations, deadlines, review submissions (return with comment or accept), view real-time department compliance tracking, download Excel/CSV reports, and receive submission/overdue alerts.
Faculty Teaching staff Self-service academic portal: view assigned courses and offerings, track upcoming/overdue deadlines, upload and resubmit files with revision history, receive in-app and email notifications (assignment, return feedback, acceptance, reminders), and maintain personal skills profile. Strict zero-trust scoping: can never see another faculty member's submissions.
Dean (Phase 2) Dean-IET Read-only executive escalation view: department-wide aggregate compliance metrics, critical risk rosters, and monthly compliance exports. Out of MVP.
System / Scheduler (internal) Automated background service Non-interactive runner: triggers scheduled reminder scans for approaching and overdue deadlines, writes in-app notifications to database, dispatches emails via SMTP/Graph, and executes nightly orphan file cleanup.

Roles are stored in the application database, not derived from the frontend. A user with a valid Microsoft sign-in but no faculty record cannot use the app.

1.3 Scope

In scope: Microsoft sign-in, faculty directory with skills and academic profile, teaching allocation (faculty to course, year, semester, section), deadlines, file submissions, progress tracking, dashboard metrics, report downloads, in-app notification center (bell, unread badge, deep-link navigation), and email notifications.

Out of scope for now: student data, attendance, marks, timetable generation, multi-department support, mobile app.

1.4 Features

Faculty directory. Name, email, designation, qualifications, skills, areas of expertise. Skills are structured tags, not free text, so the coordinator can filter "who can teach Computer Networks".

Teaching allocation. Each row answers: which faculty teaches which course, to which year, semester and section, and whether it is theory or lab. One course offering can have several faculty (theory plus lab, or co-teaching). This is the backbone: deadlines and compliance are attached to allocations.

Deadlines. The coordinator creates a deadline with a title, description, due date, type (course file, evaluation, marks upload, syllabus report, other), and who it applies to (all faculty, selected faculty, or all faculty teaching a given course or semester). Creating a deadline generates one submission slot per assignee.

Submissions. Faculty upload files against a deadline they are assigned to. Status: Pending, Submitted, Late, Returned, Accepted. The coordinator can return a submission with a comment, and the faculty member resubmits. Every version is kept.

Progress tracking. Per faculty and per deadline: submitted, late, overdue, not started. Coordinator can drill from a department number to the faculty member to the file.

Dashboard metrics. Submission rate, overdue count, on-time rate, and per-faculty compliance. The thresholds from the current SOP workbook carry over as configuration: 85% and above is On track, 60 to 84% is Watch, below 60% is Critical.

Reports. Download as Excel or CSV: submission status by deadline, compliance by faculty, allocation by semester. PDF later.

Notifications & Reminders (In-App and Email). Dual-channel notification system: (1) In-app notification center in the top navigation with live unread badge, dropdown notification list, mark-as-read, and one-click deep links to assignments or returned submissions. (2) Automated email dispatches for new deadline assignments, coordinator return comments with feedback, upcoming due date reminders (5 days and 1 day prior), and overdue escalations. The SOP workbook uses 5 days before month end as the default.

1.5 User stories

Coordinator:

  • As coordinator, I create a deadline for the course file and assign it to every faculty member teaching in semester 5, so that I do not email each person.
  • As coordinator, I see all overdue submissions in one list sorted by days overdue, so I know whom to chase today.
  • As coordinator, I open a faculty member's page and see their courses, submissions, and compliance rate, so I can prepare for reviews.
  • As coordinator, I filter faculty by skill when allocating courses, so that assignments match expertise.
  • As coordinator, I download the monthly compliance report as Excel to send to the Dean.
  • As coordinator, I return a submission with a reason, so the faculty member knows exactly what to fix.
  • As coordinator, I receive an in-app notification when a faculty member submits or resubmits work, so I can review it promptly.

Faculty:

  • As faculty, I sign in with my university Microsoft account and never create a new password.
  • As faculty, I see my courses (year, semester, section) and my pending deadlines on one screen.
  • As faculty, I see a notification bell in the header with an unread badge indicating new deadlines or feedback.
  • As faculty, I receive an email and in-app alert the moment a deadline is assigned or returned to me.
  • As faculty, I click an in-app notification to navigate directly to the relevant submission form.
  • As faculty, I upload a file against a deadline and immediately see it recorded as submitted or late.
  • As faculty, I replace a returned submission and see the coordinator's comment beside it.
  • As faculty, I keep my skills and academic details current.
  • As faculty, I can never see another faculty member's submissions.

1.4 Non-functional requirements

Security: server-side authorization on every endpoint, uploads validated and stored outside the web root, audit trail for coordinator actions. Availability: business hours matter most, nightly backups, restore tested. Scale: dozens of users and thousands of files per year, so simplicity beats horizontal scaling. Accessibility: keyboard usable, WCAG AA contrast.

1.5 Open questions that change the design

  1. Who enters syllabus coverage and class conduct: coordinator or faculty? The prototype has the coordinator entering it. Faculty self-reporting with coordinator verification scales better but needs a review flow.
  2. Are Entra accounts shared with students? Almost always yes. This decides how sign-in is restricted (section 3.2).
  3. Does the coordinator role ever rotate or become multiple people? Assume yes, so it is a role, not a hardcoded user.

2. Minimum Viable Product

The MVP must let the coordinator replace email for one full deadline cycle. Everything else waits.

In MVP

  1. Microsoft sign-in, coordinator and faculty roles, coordinator-managed faculty list.
  2. Faculty directory with skills (tags).
  3. Courses and teaching allocation (year, semester, section, theory or lab).
  4. Deadlines with assignment to selected faculty or all faculty on a course.
  5. File upload per deadline, with replace and coordinator return.
  6. Tracking view: per deadline and per faculty status, overdue list.
  7. Dashboard with four numbers: submission rate, on-time rate, overdue count, faculty at Critical.
  8. Excel export of submission status.
  9. Notifications & Reminders: in-app notification center (bell, unread badge count, mark as read, deep-link navigation) and automated email alerts (assignment, return with feedback, upcoming due date, overdue escalation).
  10. Audit log for coordinator actions.

Not in MVP (in priority order)

  1. Syllabus coverage and class/lab conduct logging, from the prototype.
  2. Achievements log.
  3. Critical observations with escalation to Dean-IET.
  4. PDF reports.
  5. WhatsApp and SMS channels (email covers the need, the others add vendor and cost).
  6. Virus scanning of uploads, unless the deployment policy requires it from day one.

The prototype's "course file, evaluation, marks upload" checklist is not a separate feature. It becomes three deadline types, so it ships with the MVP for free.

Definition of done for MVP: one real department runs one real deadline end to end, with no spreadsheet used for tracking it.

3. Architecture

3.1 Approach

A modular monolith: one Spring Boot deployable, one PostgreSQL database, one React SPA. The load is a department, not a platform, so microservices would add operational cost with no benefit. Module boundaries are enforced in code so the monolith stays clean.

Why not store files in PostgreSQL: it bloats backups and slows queries. Store metadata in the database and bytes on disk or object storage, referenced by an opaque key.

3.4 Authentication and authorization

Use the backend-for-frontend pattern. Spring Security handles the OIDC login with Entra ID (oauth2Login), keeps the session server-side, and sends the browser an HttpOnly, Secure, SameSite=Lax cookie. The SPA never holds a token. This is simpler and safer than running MSAL in the browser and validating JWTs in the API, and it fits a single-frontend app.

Rules:

  • Single-tenant app registration, tenant ID in configuration, client secret in environment variables or a secret store, never in the repo.
  • Validate the tid and oid claims. Match the user by oid, with email used only for first-time linking.
  • Restrict access to assigned users. Either enable "Assignment required" on the Entra enterprise application, or reject any login whose email is not in the pre-loaded faculty table. Do the second regardless, since students share the tenant and a tenant check alone does not stop them.
  • No self-registration. The coordinator adds faculty, the first login links the Entra oid.
  • CSRF protection stays on (cookie-based CSRF token for the SPA).
  • Authorization is enforced in the service layer with method security, for example @PreAuthorize("hasRole('COORDINATOR')") plus ownership checks. Every faculty-scoped query takes the current user's ID from the security context, never from the request. This closes IDOR by construction: a faculty member requesting another faculty member's submission gets 404, not 403.

3.5 Module structure

Package by feature, not by layer.

com.iet.dashboard
  identity/      login handling, role resolution, current user
  directory/     faculty, skills
  academics/     course, course_offering, teaching_assignment
  deadlines/     deadline, deadline_assignment
  submissions/   submission, submission_file, storage port
  tracking/      read models: status per faculty, per deadline, metrics
  reporting/     Excel/CSV export
  notifications/ in-app notification inbox & polling API, reminder scheduling, email sender, event listeners
  audit/         audit log
  shared/        error handling, pagination, config

Inside each module: web (controller, DTOs), service, domain, repo. Rules that are checked by an ArchUnit test in CI: controllers depend only on services, modules talk through each other's service interfaces, never repositories, and no entity is returned from a controller.

3.6 Data model (core tables)

  • app_user (id, entra_oid unique nullable, email unique, role, active)
  • faculty (id, user_id, name, designation, qualifications)
  • skill, faculty_skill
  • course (id, code, name, type)
  • course_offering (id, course_id, academic_year, year_of_study, semester, section) with a unique key on those columns
  • teaching_assignment (id, offering_id, faculty_id, component THEORY or LAB) unique on offering, faculty, component
  • deadline (id, title, type, due_at, created_by)
  • deadline_assignment (id, deadline_id, faculty_id, offering_id nullable) unique per deadline and faculty and offering
  • submission (id, deadline_assignment_id, status, submitted_at, reviewer_comment)
  • submission_file (id, submission_id, version, storage_key, original_name, content_type, size_bytes, sha256, uploaded_at)
  • notification (id, user_id, title, message, type, target_url, read_at nullable, created_at) unique id, indexes on (user_id, read_at) and (user_id, created_at DESC)
  • audit_log (id, actor_id, action, entity, entity_id, at, detail jsonb)

Decisions that prevent later bugs: timestamps are timestamptz in UTC, deadlines are stored as instants and displayed in Asia/Kolkata, statuses are enums with a database check constraint, foreign keys everywhere, indexes on faculty_id, deadline_id, due_at, and status. Late is computed (submitted_at > due_at), not stored as a separate flag that can disagree.

3.7 Data flow: sign-in

  1. User opens the app. SPA calls GET /api/me. Response is 401.
  2. SPA redirects to /oauth2/authorization/entra.
  3. Entra authenticates the user (university MFA applies) and redirects back with an authorization code.
  4. Spring exchanges the code for tokens on the server, validates issuer, audience and tenant.
  5. identity looks up app_user by oid, else by email. If none exists or active = false, the login is rejected with a plain "You do not have access. Contact the department coordinator." page.
  6. First login stores the oid. A session is created, the cookie is set.
  7. SPA calls GET /api/me again and receives {id, name, role}. The UI renders by role, but the backend never relies on that.

3.8 Data flow: submission upload

  1. Faculty opens a deadline they are assigned to. SPA calls GET /api/deadline-assignments/{id} (scoped to the current user).
  2. SPA sends POST /api/deadline-assignments/{id}/submissions as multipart, with a progress indicator.
  3. Controller does nothing except pass the stream and the current user to SubmissionService.
  4. SubmissionService.submit (one transaction):
    1. Load the assignment where faculty_id = current user. Missing means 404.
    2. Reject if the deadline is closed or the submission is already Accepted.
    3. Validate size (configured maximum), extension allow-list, and real content type by sniffing the bytes (Apache Tika), not the header.
    4. Stream to FileStorage.put(...), computing SHA-256 on the way. The storage key is a generated UUID path. The original file name is stored only as metadata and never used in a path.
    5. Insert submission_file (next version) and update submission status and submitted_at.
    6. Write an audit entry and emit an in-app notification to the department coordinator.
    7. If the database step fails, delete the stored file. A nightly job also removes any storage object with no database row.
  5. Response returns the updated submission DTO. SPA invalidates the relevant queries and shows Submitted or Late.
  6. Download: GET /api/submission-files/{id}/download checks ownership or coordinator role, then streams with Content-Disposition: attachment and X-Content-Type-Options: nosniff. Files are never served from a public static path.

3.9 Data flow: deadline creation and notifications

  1. Coordinator submits the deadline form with targeting rules.
  2. DeadlineService resolves targets (all faculty, selected, or by course or semester through teaching_assignment), creates deadline_assignment rows and empty submission rows with status Pending, all in one transaction.
  3. For each assigned faculty, an in-app notification row is inserted and an asynchronous email notification is queued.
  4. Notification job runs on schedule (Spring @Scheduled): checks for approaching deadlines (5 days and 1 day prior) and overdue submissions, creates in-app alerts, and dispatches reminder emails. Deduplication records prevent repeating reminders.
  5. In-app polling: The React SPA queries GET /api/notifications/unread-count every 45 seconds (TanStack Query) to display the notification badge. Clicking the bell queries GET /api/notifications; selecting an item or clicking "Mark as read" fires PATCH /api/notifications/{id}/read and deep-links to the target URL.

3.10 File storage across environments

The FileStorage interface has four methods: put, open, delete, exists. The base path or bucket comes from configuration. Development uses ./data/uploads. Production uses a dedicated directory on a mounted volume, owned by the app's service user, excluded from the web root, and included in the backup job together with the database dump. Because the app depends on the interface, moving to MinIO or S3 later is one new class and a config change. Do not build the S3 version until you need it.

3.11 Cross-cutting rules

  • Thin controllers, DTOs in and out, Bean Validation on every request.
  • One @RestControllerAdvice maps exceptions to RFC 7807 problem responses. No stack traces or SQL errors reach the client.
  • Pagination on every list endpoint (default 20, maximum 100). Dashboard queries use aggregate SQL or projections, not entity loading, to avoid N+1.
  • Rate limiting on upload and login endpoints at the proxy.
  • Structured logs with a request ID, no personal data or file contents in logs.
  • Configuration through environment variables, one profile each for dev, test, prod.
  • Frontend: every screen handles loading, empty, error, success and unauthorized states. Shared components for table, form field, status badge, file uploader and confirm dialog, so the prototype's giant single file is split up.

3.12 Testing strategy

  • Unit tests for domain rules: late computation, status transitions, threshold classification.
  • Integration tests with Testcontainers Postgres for repositories and services.
  • API tests with MockMvc for authorization: every endpoint has a test for unauthenticated, wrong role, and another user's resource.
  • Upload tests: oversized file, disallowed type, renamed executable, path traversal file name, duplicate resubmission.
  • End-to-end with Playwright for two flows: coordinator creates a deadline, faculty uploads and coordinator sees it.
  • ArchUnit tests for module boundaries.

3.13 Deployment

Docker images for backend and frontend, deployed with Docker Compose on the institution's server behind Nginx or Caddy with TLS. Flyway runs migrations at startup. Nightly pg_dump plus file directory backup, with a documented restore that has been tested once before go-live. CI (GitHub Actions) runs build, tests, and dependency scanning on every pull request.
